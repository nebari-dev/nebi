# Data & state

Three kinds of state, three homes:

| State | Where | Example |
|---|---|---|
| Component-local | `useState` | form input, open/closed, hover |
| Server data | **TanStack Query** hooks in `apps/<app>/src/hooks/` | projects, jobs, versions, registries |
| Shared client state | `apps/<app>/src/store/` | selected project id, sidebar collapsed |

Never copy server data into client state. Derive from the query instead.

> **Client-state library: Jotai** (decided; matches the OpenTeams default).
> Keep client state small. Most of what the legacy app kept in stores (mode,
> view mode, auth) goes away with the split.

## Generated API clients

Each app has its own API and its own spec:

| App | Spec | Status |
|---|---|---|
| `apps/server` | Team server OpenAPI (generated by `make swagger` from Go annotations) | Today `internal/swagger/swagger.json`, which is **Swagger 2.0** |
| `apps/client` | Client REST API's own spec (#587) | Not written yet |

Pipeline: `openapi-typescript` produces types, and `openapi-fetch` provides a
typed `fetch` client. Generated files live in `src/api/generated/` and are
never hand-edited. A `npm run gen:api` script regenerates them, and CI fails
if regenerating changes anything.

- `openapi-typescript` needs OpenAPI 3. swag emits Swagger 2.0, so either
  convert in the script (`swagger2openapi`) or move the Go side to a generator
  that emits OpenAPI 3. This is a team decision.
- Until the client API spec exists, client hooks may target the current
  endpoints through the generated server-spec types. Mark each such hook with
  `// TODO(#587): move to client API spec` so it can be found later.

Wrap the generated client once (`src/api/client.ts`). The wrapper sets the
base URL (honor the base path; the server can be mounted under a prefix),
attaches auth (bearer for the server app, the loopback session token for the
client app), and normalizes errors into one typed `ApiError` with `status`,
`code`, and `message`. Hooks call the wrapper; components never do.

## Query hooks — one file per resource

```ts
// apps/server/src/hooks/useProjects.ts
import { useMutation, useQuery, useQueryClient } from '@tanstack/react-query';
import { api } from '@/api/client';

export const projectKeys = {
  all: ['projects'] as const,
  list: () => [...projectKeys.all, 'list'] as const,
  detail: (id: string) => [...projectKeys.all, 'detail', id] as const,
};

export function useProjects() {
  return useQuery({
    queryKey: projectKeys.list(),
    queryFn: () => api.get('/projects'),
  });
}

export function useDeleteProject() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: (id: string) =>
      api.delete('/projects/{id}', { params: { path: { id } } }),
    onSuccess: () => qc.invalidateQueries({ queryKey: projectKeys.all }),
  });
}
```

- Keep query keys in a key factory per resource, exported from the hook file.
- Components get `data`, `isPending`, `error`, and so on from the hook. They
  never see `queryKey` or `api`.
- Polling (job status, logs) lives in the hook through `refetchInterval`. Stop
  polling once the job reaches a terminal state.
- Mutations invalidate the affected keys. Use an optimistic update only when
  the spec calls for one.

## Connectivity invariants

These come from real bugs in the legacy app (#217, #347, #504). They are
requirements for the new design, not patterns to copy.

**Client app (loopback):**

- The client API runs on loopback, so it stays reachable while the OS reports
  "offline". Set the QueryClient defaults to `networkMode: 'always'` for both
  queries and mutations. Never pin `'online'` in client code, or offline
  events will leave loopback queries stuck in `paused`.
- The team Server connection has three distinct states: *not configured*,
  *configured but unreachable / unauthorized*, and *connected*. Get them from
  a real reachability probe (status, `reachable`, `auth_ok`), not from "a URL
  and token are stored".
- A query whose failure shows an "unreachable" banner must recover by itself:
  give it `refetchInterval` with backoff while it's erroring.
  `refetchOnWindowFocus` is off app-wide, so window focus won't bring it back.
- The client works without a server. Remote-only UI is gated on the
  connection state and shows a clear empty or connect state. The rest of the
  UI is unaffected.

**Server app (network):**

- Use the default `networkMode: 'online'`. Pausing while offline is correct
  for a real network hop.
- On a `401`, clear the session and route to login. On a `403`, render a
  permission-denied state; don't hide data silently.
- The federated identity review flow returns a distinct error code
  (`auth.FederatedIdentityReviewErrorCode` on the backend). Check for it
  before falling through to a generic auth error.

## Forms

Use `react-hook-form` with Nebari inputs. Validate on submit, then on change
after the first submit. Show server validation errors next to the field when
the API returns field errors, and in an `Alert` otherwise. For submit
buttons, Nebari `Button` needs `render={<button type="submit" />}`.
